# 開発エージェント／Webアプリ 統合管理ダッシュボード — 要件整理

最終更新: 2026-09-02

## 位置づけ

事業仮説の検証中で、現時点（フォーム営業ツール・Webコンテンツ制作自動化）はまだどちらも未着手・実稼働なし。

本ドキュメントは「今後エージェントやWebアプリが複数稼働し始めた際に、それらを横断で一括管理・稼働監視できる画面」を、先に型として設計しておくもの。AI組織ロードマップ上の「第3線（監査ログ＋定例レビュー）」の実装先を兼ねる。

## 確定した前提

- **対象**: 今後 Claude Code で構築していくエージェント／Webアプリ全般。最初の登録対象は「フォーム営業ツール」（進め方の提案どおり、その開発と並行して着手する）。1ツール専用ではなく、後から他ツール（Webコンテンツ制作自動化等）を追加登録できる汎用設計にする
- **実装方針**: Claude Codeで作る専用のWebアプリ（スプレッドシート等の簡易一覧ではなく、認証・操作ボタン・ログ集約まで含めた本格的な管理画面）
- **開発者**: 社長は非エンジニアのため、Claude Codeが実装・保守
- **利用者範囲**: 社長＋登録した従業員。招待制のユーザー登録＋権限（管理者／閲覧者など）を分けられる設計
- **ホスティング**: ダッシュボード自体は軽量な低コストホスティングに分離して配置（例：Vercel等。フォーム営業ツール本体のクラウドVMとは別インフラでよい）
- **通知手段**: Slack（契約済みワークスペースへのIncoming Webhook等での通知。フォーム営業ツール側の障害通知もここに合わせる）

## 網羅的な項目リスト

### 1. インベントリ（何がどこにあるか）

一覧の1行＝1アプリ/エージェントとして持たせる項目。

| 項目 | 内容 |
| --- | --- |
| 愛称・アイコン | 各ツール/エージェントに付ける名前とアイコン（絵文字等）。愛着を持って運用するための表示用項目。命名の系統は未定（後日決定） |
| 名称・種別 | Webアプリ／常駐エージェント／スケジュール実行バッチ の区別 |
| 目的・担当領域 | どの業務（営業／マーケ／経理など）を担うか |
| 開発状態 | 構想中／開発中／稼働中／一時停止／廃止 |
| 起動方式 | 常時稼働（クラウドVM）／定時スケジュール／手動トリガー |
| 使用サービス・API | Claude API、microCMS、Google Drive API など主要な外部依存 |
| コードの場所 | GitHubリポジトリ等へのリンク |
| 最終デプロイ日 | いつの版が動いているか |

### 2. 稼働状況（ちゃんと動いているか）

- ステータス表示：稼働中／警告／停止／エラー を色で一目表示
- 直近の実行結果：実行日時、処理件数、成功率
- 次回実行予定：スケジュール系ジョブの次回起動時刻
- ヘルスチェック：外形監視（生死確認）。無人クラウド常時稼働のものは特に重要
- 直近のエラーログ：内容と発生時刻

### 3. アクセス・操作（一律に開ける／動かせる）

- 各アプリの管理画面・ダッシュボードへのワンクリックリンク
- （可能なものは）手動での起動／停止／再実行ボタン
- ログイン情報そのものはここに置かず、パスワードマネージャー等へのリンクに留める

### 4. アラート・通知

- 異常時の通知先（Slack）と発報条件（例：3回連続失敗、24時間実行なし）
- 通知が実際に届いているかの確認手段

### 5. ログ・監査（三線防御の第3線）

- 実行ログの保存場所へのリンク（詳細ログは要約＋リンクに留める）
- 月次レビューの実施記録
- 査読/ファクトチェックAgentのようにリスクスコアを持つものは、スコア推移も表示

### 6. コスト管理

- サービスごとの月額固定費（クラウドVM代など）
- 従量課金の実績（Claude API利用料など）と予算超過アラート

### 7. セキュリティ・権限

- 各エージェントが持つAPIキーの権限範囲・最終ローテーション日（キー自体は表示しない）
- アクセスできる人の一覧（招待制ユーザー管理、管理者／閲覧者などのロール分け）
- この管理画面自体の認証（全エージェントへの入口を束ねる場所のため、ここが最弱点にならないよう最優先で設計）

### 8. ドキュメント・引き継ぎ

- 各アプリの仕様書・要件整理（本プロジェクト内の他ドキュメント等）へのリンク
- 障害時の対応手順（誰が何をするか）

## 画面イメージ

- **一覧画面**: 1行＝1アプリで「アイコン／愛称／状態●／直近実行結果／成功率／次回実行予定／[開く]ボタン」が並ぶ形。
- **詳細画面**: 行をクリックすると、そのアプリの実行ログ・コスト・APIキー権限・仕様書リンクなどの詳細に遷移。

## MVPスコープ（最初に作る範囲）

表示するものがまだない段階でフル機能を作っても仕方がないため、着手時は以下の3点に絞る。

1. インベントリ一覧（上記1番）
2. 稼働状況表示（上記2番）
3. Slackアラート通知（上記4番）

コスト管理・詳細監査ログ・ドキュメント集約（上記5・6・8番）はPhase 2以降。

## Claude Codeへの依頼文（たたき台）

着手タイミングはフォーム営業ツール本体の開発と合わせてで問題ない。以下はそのまま貼り付けられる依頼文。

> Sales Bond で開発するAIエージェント・Webアプリを一括管理するダッシュボードを作りたいです。
>
> まずはMVPとして、以下の3機能に絞った最小版を作ってください。
>
> **【対象】**
> 最初の登録対象は「フォーム営業ツール」（問い合わせフォーム経由のアウトバウンド自動送信システム、現在別途開発中）です。ただし今後エージェントやWebアプリが増えていく前提なので、対象を後から追加登録できる汎用的な設計にしてください（1つのツール専用ではなく、複数ツールを横断管理できるデータ構造にする）。
>
> **【MVPで実装してほしい機能】**
>
> 1. インベントリ一覧
>    - 登録した各ツールについて：愛称・アイコン、名称・種別（Webアプリ／常駐エージェント／スケジュールバッチ）、目的・担当領域、開発状態、起動方式、使用サービス・API、コードの場所（GitHubリンク）、最終デプロイ日を表示・編集できる
> 2. 稼働状況表示
>    - 各ツールのステータス（稼働中／警告／停止／エラー）を色で一覧表示
>    - 直近の実行結果（実行日時・処理件数・成功率）
>    - 次回実行予定
>    - 直近のエラーログ
>    - 各ツール側から状態を報告してもらうための共通API（またはログ書き込み方式）を設計し、それに合わせてフォーム営業ツール側にも状態報告の実装を入れてください
> 3. アラート通知
>    - 異常時（例：3回連続失敗、24時間実行なし）にSlackへ通知する（Slackワークスペースは契約済み。Incoming Webhook等でシンプルに送れる形でお願いします）
>
> **【アクセス・認証】**
> - 利用者は社長＋登録した従業員です。招待制のユーザー登録と、権限（管理者／閲覧者など）を分けられる作りにしてください
> - 各ツールの管理画面へのワンクリックリンクも一覧に含めてください（ログインID/パスワード自体はこの画面に保存せず、リンク遷移のみ）
>
> **【ホスティング】**
> - このダッシュボード自体は軽量な低コストホスティング（Vercel等、他に適したものがあれば提案してください）に分離して配置してください。フォーム営業ツール本体（クラウドVMで常時稼働）とは別インフラで構いません
>
> **【セキュリティ】**
> - 各ツールが使うAPIキーは、この画面には権限範囲とローテーション予定のみを表示し、キー自体は表示・保存しないでください
> - 誰が何をしたかの操作ログを残してください
> - 最小権限の原則で設計してください
>
> **【今回はスコープ外（Phase 2以降でOK）】**
> - コスト管理（月額費用の自動集計）
> - 詳細な監査ログ・月次レビュー機能
> - ドキュメント・仕様書リンク集約
>
> 不明点があれば、実装前に質問してください。

## 開発に着手する際に必要な情報（チェックリスト）

- 認証方式 → 決定済み（社長＋登録した従業員、招待制・権限分け）
- ホスティング環境 → 決定済み（軽量な低コストホスティングに分離）
- 通知の受け取り方法 → 決定済み（Slack）
- 各エージェント側の実装：管理画面が状態・ログを取得できるよう、各エージェント側に「状態を報告する」共通の仕組み（API/ログ出力形式）を最初から統一しておく必要がある（依頼文に反映済み）
- 愛称・アイコンの命名系統：社名「絆」テーマ／和風の愛称／動物モチーフ／英語コードネーム風、などの案から後日決定。決まり次第、既知のエージェント（フォーム営業ツールの送信Bot、Webコンテンツ制作の各Agent等）に具体名を付ける

## 進め方の提案

今このダッシュボードだけを空の状態で作っても表示するものがないため、最初の実装対象（フォーム営業ツール）の開発と並行して、このダッシュボードのMVP（インベントリ＋稼働状況＋Slackアラートの3点）を一緒に作るのが効率的。以降に追加するエージェントは、最初から「このダッシュボードに状態を報告する」前提で作ることで、後付けの手間がなくなる。
